# Read-only RingMaster assistant

## Pilot behavior

The global rabbit opens a text AI panel. Idle/thinking animation runs locally and respects reduced motion. Page-shell screens supply a title/show ID; other screens fall back to a general context. No widget scraping, screenshots, form contents or QR tokens are sent to the model. The mascot uses a bundled realistic rabbit portrait, so another animal asset can be added later without changing the data boundary.

Suggested questions are selected locally from the current screen (shows, entries, entry cart, animals, household/account settings, show setup, reports and closeout), with general suggestions on other screens. Opening help makes no AI request or private-record lookup. General questions use reviewed help instructions. The panel routes clearly worded questions to entries, reports/legs, household exhibitors, setup, or show report status. General how-to questions use help guidance. Chester asks which show in the conversation when a record question has no show context; the user can search/select it then, or cancel and ask something else. Unrecognized subjects stay in general help; this is conservative phrase routing, not unrestricted AI database access. The model can invoke only one zero-argument tool, bound on the server to that selection. A show is required for show-specific lookups. Results are limited to 31 rows with a truncation flag; only selected fields are returned. Report status does not assert email delivery, diagnose every readiness blocker, or prove payment. Reply links to Entries, Reports, Animals, Account, Household, Shows and Show management are application-controlled, not generated by the AI. Links to carts lead to the show list so users select their existing cart. Management links use the selected show when available and retain the destination screen’s permission checks. Reply provenance labels are not displayed.

Help guide articles and Contact support work without an AI key or after the budget cutoff. Contact support opens a user-reviewable email in the user's mail app; nothing is automatically sent. No inbox content is ingested.

## Permissions and privacy

- Edge Function validates the actual bearer token with `getUser`; anonymous sessions cannot call the AI.
- All domain reads use the caller's authenticated Supabase client. SQL read RPCs are SECURITY INVOKER and retain RLS, with additional explicit household filters.
- A selected owner must pass `can_access_household` for the actual caller, including accepted and unrevoked membership. Supplying another person's email/name/ID cannot grant access.
- Household access does not grant secretary roles. Setup and closeout require `user_can_manage_show_settings(show, auth.uid())`.
- The reports lookup reuses the existing authorized household report reader, discarding storage paths, emails, and report bodies before model input.
- The service client is used only for spending reservations and usage settlement, never domain data. These metering RPCs are service-role-only and cannot be selected by the model.
- Chat and draft text are held in memory across panel closes and page navigation. Clear chat removes them. Browser refresh clears the session; nothing is written to browser storage. Account/household/support-context changes replace the chat session, close the panel and discard in-flight UI results. Leaving while an AI request is pending records an interrupted message; it does not automatically retry or release its spending hold. Support impersonation is disabled for AI use.
- OpenAI requests use `store: false`. This is not a claim of zero provider retention; configure provider data policies separately as needed.
- Usage records contain random request/conversation IDs, actor ID, topic, model, tokens, cost estimate and status. No raw questions, answers, database results or provider error bodies are persisted or logged.

## Four overage controls

1. **Per-user limits:** 20 questions per UTC day, 3 per rolling minute, one active question per actor. Failed requests count. Limits cannot be reset by clearing chat or switching households.
2. **Focused lookups:** one question topic/show, one lookup, at most two AI calls. 1,800 characters/question, six bounded history messages, 14KB inbound body ceiling, 20KB serialized provider request ceiling, 1,200 output tokens per call (including reasoning). No hosted search tools, agents, retry loops, voice or image processing.
3. **Usage tracking:** Superadmin → AI Assistant Usage shows estimated/reserved monthly spending, tokens via the RPC, question/conversation counts, and cost for each of the latest 30 conversations. It does not store transcripts.
4. **Spending cutoff:** $25/month default, disabled until activated. Reserve $0.06 atomically before contacting OpenAI under a short row lock; concurrent reservations see committed holds. Settle successful requests to rounded-up token cost. Failure/timeout/crash retains the full hold indefinitely; do not automatically release unknown charges. Missing metering, invalid settings, or missing API key fail closed. Pausing retains help/support.

Fixed model: `gpt-5.4-mini`, standard rates of $0.75/M input and $4.50/M output as verified 2026-09-18. No cache discount is assumed. Two calls at a conservative 24,000 input-token bound (20KB request + 4K framing allowance) and 1,200 output tokens cost at most $0.0468, below the $0.06 hold. These are application estimates, not an invoice guarantee. Rate changes, taxes and usage from other API keys/services are outside this meter. Use a dedicated OpenAI project/key. Reverify pricing and the upper bound before changing model, tools, prompt size or output limit. A measured cost above the reservation automatically pauses future AI requests.

Monthly accounting uses request-start UTC month. Requests spanning midnight at a month boundary stay charged to the starting month. Unknown charges intentionally reduce available budget until a human reconciles them against provider billing. Do not delete usage rows to reset limits. Usage keeps the pseudonymous actor ID after account deletion so deleting an account cannot release already-spent monthly funds.

## Activation / deployment

This feature ships paused. Build and local tests do not send customer records to OpenAI.

1. Apply `20260919014108_add_read_only_show_assistant.sql` after the existing household migration. Do not push unrelated pending migrations accidentally.
2. Set the server-side `OPENAI_API_KEY` in Supabase Edge Function secrets. Never put it in Dart, public environment variables, Git, documentation, or chat. Standard Supabase function secrets (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`) are also required.
3. Deploy `show-assistant` with JWT verification enabled and build/deploy the Flutter web app.
4. Run hosted database advisors and a controlled authenticated smoke test: self/household entries, stranger denial, secretary denial, and paused behavior. Confirm model access with a synthetic record before real use.
5. In Superadmin → AI Assistant Usage, set the desired budget and enable AI answers.

No production database, secrets, deployment or paid provider requests are changed by the local build workflow.

## Verified guide references

The six Scribe guides already listed in Secretary Resources were read on 2026-09-19. `supabase/functions/show-assistant/guides.json` records reviewed topic ranges, source URLs, and the verification date. `lib/services/assistant_guide_catalog.dart` is its client projection; a test detects mismatched titles, URLs and step ranges. Reverify and update both files when guides change.

Prepared replies append relevant reference IDs. AI receives the same bounded topic catalog in its instructions and can emit `[[guide:ID]]`; the app strips markers and only renders recognized IDs as links with trusted guide titles and verified Scribe step numbers. Unknown IDs and arbitrary URLs never become links. Links open the whole guide and display the relevant step number/range; they do not claim a direct scroll-to-step anchor. Scribe guide numbers differ from application closeout stage numbers. No guide text is scraped at question time, and existing request size, token and spend caps remain enforced. No step citation is invented for topics missing from the catalog. The older Stripe guide is labeled for Stripe and must not be generalized to Square.

Website help links and Secretary Resources remain available under FAQ. External guides open separately and retain Chester's in-memory conversation. Production AI behavior still requires deploying the updated Edge Function; no paid provider request was made during local verification.

The FAQ replaces the former short Help guide list. It uses the same prepared-answer catalog as starter replies, prioritizes questions for the current screen, provides text search, and includes trusted page links and verified Scribe references. Browsing FAQs does not invoke AI or clear the conversation.

Contact support previews a readable email body with screen, topic, show, conversation ID, every user/Chester message in order, verified guide references, and any unsent draft. No transcript truncation is applied. Mailto uses percent-encoded spaces instead of form-style plus signs. The user opens and sends the email themselves; Copy full message is available for mail clients that limit URL length. This exports the current in-memory chat only, not conversations cleared by refresh, sign-out, household switch, or Clear chat. It does not create a permanent server transcript archive.

## Saved Chester conversations

Super Admin → Chester Conversations provides paginated conversation lists (50 at a time) and complete, paginated transcripts (100 messages per page). It shows the actual signed-in account email, timestamps, screen, topic, user/Chester speaker, prepared/AI sources, guide references, FAQ expansions, support openings, and unavailable-AI events. Unsent drafts and FAQ search text are not archived. These are client-reported interactions, not tamper-proof provider audit records.

Migration `20260919162349_add_chester_conversation_review.sql` must follow the original assistant migration. Both conversation tables are private with RLS enabled and no client table privileges. Append RPCs derive identity from `auth.uid()`, enforce conversation ownership, immutable messages, idempotent event IDs, length bounds, and a 2,000-event daily cap. Review RPCs check the existing `is_super_admin(auth.uid())` guard. Client chat recording is disabled when signed out or impersonating another user. Recording adds no AI requests. Clearing the visible chat starts a new ID and does not delete saved history; account deletion cascades to its transcript records.

The append queue survives page changes in the active session and retries failed saves on later interactions. Save failures produce a visible notice; offline/failed pending saves can be lost on refresh. Signed-in users see a support-review notice in Chester's footer. No historic conversations can be backfilled from previous in-memory sessions. No production migration has been applied as part of local implementation. Transactional SQL permission tests are in `supabase/tests/chester_conversations.sql`.

## Reviewed reusable answers

Super Admin → Chester Conversations → Create FAQ draft copies a selected Chester reply and its preceding question into a private draft, without an AI request. Obvious email addresses (question and answer) and UUIDs (answer) are redacted; names and other private facts still require human review. The editor supports a main question, up to 20 matching variants, reusable steps, and up to three verified guide references. Existing application page-name link rendering applies to reviewed replies.

Chester Reviewed Answers lists drafts and published answers. Only Super Admins can create, edit, publish, or unpublish. Publishing requires an explicit accuracy/privacy review checkbox. Editing a published answer changes its draft only; a separate approved snapshot remains live until republished. Version checks reject stale edits; unique normalized matching questions reject conflicting publications. Unpublishing removes all matches immediately for subsequent requests. Replies already displayed in a chat are retained in that conversation.

Signed-in Chester checks the published match RPC before built-in answers or AI. Matching ignores capitalization, typographic apostrophes, repeated whitespace and ending punctuation, but uses no semantic guessing. Approved questions must use general how-to prefixes; personal status questions are not eligible for publication. No user records or source transcript metadata are returned by the matching RPC. If lookup is unavailable, existing prepared/AI behavior remains available. Published answer matching incurs no OpenAI request; it is not model fine-tuning. Unsent drafts and entire conversations are never automatically sent for training.

The reviewed-answer migration was applied to the live project on 2026-09-19; the new UI is available in the local preview and requires the normal app release for all users. No answers were published during setup.
